# Documentación de Bases de Datos — Módulo Design

**Ruta código:** `lib\design\`
**Fecha:** 2026-08-13

## 1. Separación de Estructuras

### Estructuras internas (NO van a CouchDB)
- `DesignToken` (`data_models\design_token.dart`): token individual de diseño; hoy no persiste (config estática en app).
- `ThemeState` (`data_models\theme_state.dart`): estado observable Riverpod in-memory.
- `SocialThemeData` (`tokens\social_theme_data.dart`): envoltorio de `ThemeData` Material; runtime, no BD.
- `AdaptiveLayout` (`widgets\`): widget UI.
- `DesignEngine`, `ThemeNotifier`: lógica/estado Riverpod.

### Estructuras que van a Base de Datos (potencial)
- **`ThemeTokenSet`** (`repositories\theme_repository.dart`): conjunto de tokens de un tema. Si la plataforma permite personalizar/subir temas desde el backend, `ThemeTokenSet` (y sus `DesignToken`) deberían persistirse.
- **`ThemeState.themeId`**: identificador del tema seleccionado por el usuario; debería persistirse en el perfil del usuario (`motorsocial_usuarios`) como preferencia.

> **Importante:** Flutter **nunca posee credenciales CouchDB**; persiste vía backend Express. El `ThemeRepository` es la abstracción. Lo siguiente describe cómo **debería** persistirse en CouchDB si se hace configurable.

## 2. Estructura: `ThemeTokenSet` (potencial)

**Descripción:** Conjunto de tokens de diseño que definen un tema (light/dark/custom).

### Diccionario de Datos

| Campo | Tipo Dart | Tipo JSON | Req | Descripción |
|---|---|---|---|---|
| `tokens` | `Map<String, DesignToken>` | `object` | ✓ | Mapa de tokens indexados por `key` |

#### `DesignToken`

| Campo | Tipo Dart | Tipo JSON | Req | Descripción |
|---|---|---|---|---|
| `key` | `String` | `string` | ✓ | Clave del token (`color.primary`, `text.body`, …) |
| `category` | `String` | `string` | ✓ | Categoría (`color`, `typography`, `spacing`, …) |
| `value` | `String` | `string` | ✓ | Valor del token (`#FF6750A4`, `14`, `1.5`, …) |

### Formato JSON Esperado

```json
{
  "_id": "theme:light_default",
  "type_doc": "ThemeTokenSet",
  "themeId": "light_default",
  "mode": "light",
  "tokens": {
    "color.primary": { "key": "color.primary", "category": "color", "value": "#FF6750A4" },
    "text.body": { "key": "text.body", "category": "typography", "value": "14" }
  }
}
```

### CouchDB — `motorsocial_themes` (sugerida)

#### Consultas (Mango)
**1. Cargar tema por id**
```json
{
  "selector": {
    "type_doc": "ThemeTokenSet",
    "themeId": "light_default"
  },
  "limit": 1
}
```

#### Índices
```json
{ "index": { "fields": ["themeId"] }, "name": "idx_theme_id", "type": "json" }
```

## 3. Preferencia de tema del usuario (`ThemeState.themeId`)

El `themeId` seleccionado debería persistirse como campo del perfil de usuario en `motorsocial_usuarios`:

```json
{
  "_id": "user:9999",
  "type_doc": "SocialUser",
  "...": "...",
  "preferredThemeId": "light_default"
}
```

Ya documentado en `identity\06_BD.md`; añadir el campo `preferredThemeId` al modelo `SocialUser` (hoy no lo tiene).

## 4. Estado Actual del Módulo

- `ThemeRepository` (abstract) define `loadTheme(themeId) → ThemeTokenSet` pero **no tiene implementación concreta** (no hay `InMemoryThemeRepository` ni uno de backend).
- `DesignToken` y `ThemeTokenSet` **no** tienen `fromJson`/`toJson`; deben añadirse para persistir.
- `ThemeState` existe pero no está cableado al `ThemeNotifier` (`Notifier<void>`, sin estado).
- `SocialThemeData` no se construye dinámicamente desde `ThemeTokenSet`; hoy es estático.
- **No hay `themeRepositoryProvider`** (deuda técnica; añadir al cablear).
- AGENTS.md exige usar el ColorScheme global `appTheme` (referenciado en `var_color_themes.dart`, inexistente); este módulo no lo provee aún.
