# Documentación de Bases de Datos — Módulo Social Graph

**Ruta código:** `lib\social_graph\`
**Fecha:** 2026-08-13

## 1. Separación de Estructuras

### Estructuras internas (NO van a CouchDB)
- `SocialQuery` (`providers\social_query.dart`): contrato de consulta vacío, reservado.
- `GroupState` (`providers\group_notifier.dart`): estado observable Riverpod in-memory.
- `SocialGraphEngine` (`engine\`): contenedor `const`, `initializeProviders` no-op.
- Los contratos abstractos `RelationshipsRepository`, `InvitationsRepository`, `GroupsRepository`, `SocialGraphRepository` y sus implementaciones `InMemory*` (devuelven `[]`/no-op).

### Estructuras que van a Base de Datos
Cuatro modelos de dominio serializables/serializables-pendinges:
- **`SocialRelationship`** (con `fromJson`) — relaciones de contacto.
- **`Invitation`** (con `fromJson`) — invitaciones.
- **`SocialInvitation`** (sin `fromJson`, pendiente) — variante de invitación.
- **`SocialGroup`** (sin `fromJson`, pendiente) — grupos.

> **Importante:** Flutter **nunca posee credenciales CouchDB**; persiste vía backend Express (Node.js + `nano`). Los repositorios son abstracción. Lo siguiente describe cómo **debería** persistirse en CouchDB.

## 2. Estructura: `SocialRelationship`

**Descripción:** Relación dirigida entre dos usuarios (p. ej. contacto, follow, bloqueo).

### Diccionario de Datos

| Campo | Tipo Dart | Tipo JSON | Req | Descripción |
|---|---|---|---|---|
| `id` | `String` | `string` (`_id`) | ✓ | ID único (prefijo `relationship:`) |
| `actorId` | `String` | `string` | ✓ | Usuario origen |
| `targetId` | `String` | `string` | ✓ | Usuario destino |
| `type` | `String` | `string` | ✗ | Tipo de relación (`contact`, `follow`, `block`…); por defecto `'contact'` |
| `createdAt` | `DateTime` | `string` ISO-8601 | ✓ | Fecha de creación |

### JSON Esperado
```json
{
  "_id": "relationship:uuid",
  "type_doc": "SocialRelationship",
  "actorId": "user:9999",
  "targetId": "user:1111",
  "type": "contact",
  "createdAt": "2026-08-13T15:00:00.000Z"
}
```

> **Colisión de `type`:** el campo Dart `type` (tipo de relación) colisiona con el discriminador CouchDB `type`. Sugerido renombrar a `type_doc` o `relationship_type` al persistir (igual que en Security/Catalog).

### CouchDB — `motorsocial_social_graph`

#### Consultas (Mango)
**1. Relaciones por actor**
```json
{
  "selector": {
    "type_doc": "SocialRelationship",
    "actorId": "user:9999"
  },
  "sort": [{ "createdAt": "desc" }],
  "limit": 50
}
```

**2. Relaciones por destino**
```json
{
  "selector": {
    "type_doc": "SocialRelationship",
    "targetId": "user:1111"
  },
  "sort": [{ "createdAt": "desc" }],
  "limit": 50
}
```

#### Índices
```json
{ "index": { "fields": ["actorId", "createdAt"] }, "name": "idx_actor_created_at", "type": "json" }
{ "index": { "fields": ["targetId", "createdAt"] }, "name": "idx_target_created_at", "type": "json" }
```

## 3. Estructura: `Invitation` / `SocialInvitation`

**Descripción:** Invitación dirigida entre dos usuarios para iniciar una relación.

### Diccionario de Datos (`Invitation`)

| Campo | Tipo Dart | Tipo JSON | Req | Descripción |
|---|---|---|---|---|
| `id` | `String` | `string` (`_id`) | ✓ | ID único (prefijo `invitation:`) |
| `senderId` | `String` | `string` | ✓ | Usuario emisor |
| `recipientId` / `receiverId` | `String` | `string` | ✓ | Usuario receptor (nomenclatura divergente entre `Invitation` y `SocialInvitation`) |
| `status` | `String` | `string` | ✗ | `pending` (def), `accepted`, `rejected` |
| `createdAt` | `DateTime` | `string` ISO-8601 | ✓ | Fecha de creación |

### JSON Esperado
```json
{
  "_id": "invitation:uuid",
  "type_doc": "Invitation",
  "senderId": "user:abc",
  "recipientId": "user:xyz",
  "status": "pending",
  "createdAt": "2026-08-13T15:00:00.000Z"
}
```

### CouchDB — `motorsocial_invitations` (sugerida)

#### Consultas (Mango)
**1. Invitaciones pendientes para un receptor**
```json
{
  "selector": {
    "type_doc": "Invitation",
    "recipientId": "user:xyz",
    "status": "pending"
  },
  "sort": [{ "createdAt": "desc" }],
  "limit": 50
}
```

#### Índices
```json
{ "index": { "fields": ["recipientId", "status", "createdAt"] }, "name": "idx_recipient_status_created_at", "type": "json" }
{ "index": { "fields": ["senderId", "createdAt"] }, "name": "idx_sender_created_at", "type": "json" }
```

## 4. Estructura: `SocialGroup`

**Descripción:** Grupo de usuarios (comunidad dentro de la plataforma).

### Diccionario de Datos

| Campo | Tipo Dart | Tipo JSON | Req | Descripción |
|---|---|---|---|---|
| `id` | `String` | `string` (`_id`) | ✓ | ID único (prefijo `grupo:` según AGENTS.md) |
| `name` | `String` | `string` | ✓ | Nombre del grupo |
| `memberIds` | `List<String>` | `array<string>` | ✗ | IDs de miembros (def `[]`) |
| `isPublic` | `bool` | `boolean` | ✗ | Visibilidad pública (def `true`) |

### JSON Esperado
```json
{
  "_id": "grupo:uuid",
  "type_doc": "SocialGroup",
  "name": "Talleres del barrio",
  "memberIds": ["user:abc", "user:xyz", "user:9999"],
  "isPublic": true
}
```

### CouchDB — `motorsocial_grupos` (sugerida; AGENTS.md cita prefijo `grupo:`)

#### Consultas (Mango)
**1. Grupos descubribles (públicos y unibles)**
```json
{
  "selector": {
    "type_doc": "SocialGroup",
    "isPublic": true
  },
  "limit": 50
}
```

**2. Grupos de un usuario (miembro)**
```json
{
  "selector": {
    "type_doc": "SocialGroup",
    "memberIds": { "$elemMatch": { "$eq": "user:abc" } }
  },
  "limit": 50
}
```

#### Índices
```json
{ "index": { "fields": ["isPublic"] }, "name": "idx_is_public", "type": "json" }
{ "index": { "fields": ["memberIds"] }, "name": "idx_member_ids", "type": "json" }
```

> **Nota:** el índice sobre `memberIds` (array) requiere soporte de CouchDB para índices multi-key; alternativamente, usar una vista MapReduce `by_member` que emita por cada `memberId`.

#### Vistas (MapReduce alternativas)
- **Vista `by_member`** (`map`): `doc.memberIds.forEach(m => emit(m, doc._id))`.

- `SocialGroup` y `SocialInvitation` no tienen serialización — añadirla al cablear el backend.
