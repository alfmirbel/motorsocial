# Documentación de Bases de Datos - Módulo Core / Infraestructura

> **Contexto:** el módulo Core **no define modelos de dominio que persistan
> directamente a CouchDB**. Su rol es proporcionar la **capa de conexión y
> abstracción** (configuración de conexión, repositorio base CRUD y modelo
> de registro vectorial) que los módulos de dominio (identity, catalog,
> activity, media, social_graph, location, …) usarán para persistir sus
> propias estructuras. Las bases de datos de negocio se documentan en cada
> módulo de dominio (p. ej. `motorsocial_usuarios` en Identity,
> `motorsocial_alimentos` en Catalog, `motorsocial_log_calorias` en
> Catalog/Resilience, `motorsocial_activity_feed` en Activity).
>
> Aquí se documentan: (1) las **estructuras internas** de configuración/conexión
> (no se persisten) y (2) el **repositorio base `CouchDbRepository`** cuyas
> operaciones se aplican sobre cualquier base `motorsocial_*`.

---

## 1. Estructuras internas (NO van a CouchDB)

### 1.1 `SocialAppConfig` (configuración de aplicación — en memoria / build-time)
Clase `@immutable` de `lib\core\config\social_app_config.dart`. Se construye
en tiempo de arranque (realmente hoy solo se define; el cableado de raíz de
`main.dart` vive en otros módulos). **No se persiste como documento CouchDB.**

**Diccionario de datos:**

| Campo | Tipo Dart | Default | Descripción |
| :--- | :--- | :--- | :--- |
| `appName` | `String` | `'MotorSocial'` | Nombre comercial de la app |
| `themeId` | `String` | `'light_default'` | Identificador del tema activo |
| `identity` | `Map<String, dynamic>` | `{}` | Config específica del módulo identity |
| `navigation` | `Map<String, dynamic>` | `{}` | Config del módulo navigation |
| `location` | `Map<String, dynamic>` | `{}` | Config del módulo location |
| `catalog` | `Map<String, dynamic>` | `{}` | Config del módulo catalog |
| `media` | `Map<String, dynamic>` | `{}` | Config del módulo media |
| `activity` | `Map<String, dynamic>` | `{}` | Config del módulo activity |
| `modules` | `List<String>` | `[]` | Lista de módulos activos |
| `useStubRepositories` | `bool` | `true` | Si `true`, se usan repositorios en memoria |
| `couchdb` | `CouchDbConfig?` | `null` | Conexión CouchDB (nulo si no se usa) |
| `qdrant` | `QdrantConfig?` | `null` | Conexión Qdrant (búsqueda vectorial) |

**JSON serializado (in-memory, no doc CouchDB):**

### 1.2 `CouchDbConfig` (credenciales de conexión — **sensibles**)
Definida **dos veces** (en `social_app_config.dart` y en `couchdb_repository.dart`),
misma forma. No se persiste. Las credenciales reales se obtienen vía
`String.fromEnvironment()` / `defines.json` (ver AGENTS.md) en otros módulos.

| Campo | Tipo Dart | Default | Descripción |
| :--- | :--- | :--- | :--- |
| `url` | `String` | `'http://localhost:5984'` | URL raíz del servidor CouchDB |
| `username` | `String` | `''` | Usuario admin CouchDB |
| `password` | `String` | `''` | Password (secreto — **no documentar valor**) |

### 1.3 `QdrantConfig` (conexión al almacén vectorial — sensible)

| Campo | Tipo Dart | Default | Descripción |
| :--- | :--- | :--- | :--- |
| `url` | `String` | `'http://localhost:6333'` | URL del servidor Qdrant |
| `apiKey` | `String` | `''` | API key de Qdrant |

### 1.4 `QdrantRecord` (modelo de resultado — no se persiste en CouchDB)
`lib\core\database\qdrant_repository.dart`. Resultado de una búsqueda
vectorial (cuando `QdrantRepository` se implemente).

| Campo | Tipo Dart | Default | Descripción |
| :--- | :--- | :--- | :--- |
| `id` | `String` | (obligatorio) | Identificador del punto/vector |
| `payload` | `Map<String, dynamic>` | (obligatorio) | Características arbitrarias asociadas |
| `score` | `double?` | `null` | Relevancia del resultado |

## 2. Repositorio base `CouchDbRepository` (operaciones genéricas)

`lib\core\database\couchdb_repository.dart`. Cliente HTTP mínimo sobre
`package:http`. Opera sobre **cualquier** base `motorsocial_*` pasada como
parámetro `db` en cada método. **No pertenece a una BD concreta**; es la
capa base reutilizable por todos los módulos de dominio.

### 2.1 Métodos y su contrato HTTP

| Método Dart | Verbo / Ruta HTTP | Status exitoso | Retorna / Lanza |
| :--- | :--- | :--- | :--- |
| `ping()` | `GET {url}/` (root server) | `200` | `bool` |
| `createDatabase(db)` | `PUT {url}/{db}` | `201` o `412` | `bool` |
| `ensureDatabase(db)` | (compone `ping` + `createDatabase`) | — | `bool` |
| `get(db, id)` | `GET {url}/{db}/{id}` | `200` | `Map<String,dynamic>?` (null si no existe) |
| `put(db, doc)` | `POST {url}/{db}` (si `doc` no tiene `_id`) o `PUT {url}/{db}/{_id}` | `200` o `201` | `String` (id resultante) — lanza `CouchDbException` en otro caso |
| `delete(db, id, rev)` | `DELETE {url}/{db}/{id}?rev={rev}` | `200` | `void` — lanza `CouchDbException` en otro caso |
| `queryView(db, design, view, {key, startKey, endKey, descending, limit})` | `GET {url}/{db}/_design/{design}/_view/{view}?include_docs=true&...` | `200` | `Map<String,dynamic>` — lanza `CouchDbException` en otro caso |
| `close()` | — | — | cierra el `http.Client` |

### 2.2 Cabeceras (todas las peticiones)
```
Content-Type: application/json
Accept: application/json
Authorization: Basic base64(username:password)
```

### 2.3 Convenio de Doc IDs (heredado de AGENTS.md — aplicado por los módulos)
- Prefijo semántico + UUID: `user:`, `propiedad:`, `mensaje:`, `grupo:`,
  `activity:`, `propiedad:`, etc. (definidos por cada módulo de dominio).
- `put` decide método (POST/PUT) según la **presencia de `_id`** en el `doc`,
  lo que permite tanto altas auto-generadas como actualizaciones con un mismo
  método.

## 3. Bases de datos CouchDB afectadas por este módulo

Core **no es dueño de ninguna BD `motorsocial_*`**. La siguiente tabla enumera las BD de negocio (los nombres se toman de AGENTS.md y se
documentarán por cada módulo de dominio) que se acceden mediante este
repositorio base cuando `useStubRepositories = false`:

| Nombre CouchDB | Módulo dueño | Estructura principal | Doc ID prefijo |
| :--- | :--- | :--- | :--- |
| `motorsocial_usuarios` | Identity | Usuario / perfil | `user:` |
| `motorsocial_alimentos` | Catalog | Alimento / producto | (definido en Catalog) |
| `motorsocial_log_calorias` | Catalog / Resilience | Log de calorías | (definido en su módulo) |
| `motorsocial_perfil_nutricional` | Identity / Catalog | Perfil nutricional | (definido en su módulo) |
| `motorsocial_activity_feed` | Activity | SocialActivity | `activity:` |

> **Referencia cruzada:** las consultas Mango, índices y vistas concretas de
> cada BD se definen en el `06_BD.md` de cada módulo de dominio. Core solo
> provee el mecanismo (`queryView` para MapReduce y — cuando se implemente —
> el helper Mango).

## 4. Consultas (Mango Queries) — mecanismo base

`CouchDbRepository` **no expone hoy un helper Mango dedicado**; los módulos
de dominio deberían componer sus `selector`/`sort`/`limit` y enviarlos vía
`put(db, ...)` a `_find` o ampliar el repositorio base con un método
`findMango(db, selector, {sort, limit, skip, fields})`. Se recomienda, según
AGENTS.md, **preferir Mango sobre MapReduce**; el método actual `queryView`
queda reservado para vistas legacy.

### 4.1 Esquema recomendado (a implementar en Core o en cada módulo)
```json
POST {url}/{db}/_find
{
  "selector": { "<campo>": { "<op>": "<valor>" } },
  "sort": [ { "<campo>": "desc" } ],
  "limit": 20,
  "skip": 0,
  "fields": ["_id", "_rev", "<campo>"]
}
```

### 4.2 Índices Mango (a definir por cada módulo)
```json
POST {url}/{db}/_index
{
  "index": { "fields": ["<campo>", "<campo2>"] },
  "name": "idx_<nombre>",
  "type": "json"
}
```

> Pendiente: ampliar `CouchDbRepository` con `findMango(db, query)` y
> `ensureIndex(db, index)` para estandarizar en Core este mecanismo.

---

## 5. Vistas / Queries (MapReduce)

El único mecanismo de "vista" hoy expuesto por Core es `queryView(db,
design, view, {key, startKey, endKey, descending, limit})`, que llama a
`_design/{design}/_view/{view}` con `include_docs=true`. No se definen vistas
propias del módulo Core; las definen los módulos de dominio que todavía usan
MapReduce. Se sugiere migrar las consultas a Mango en futuras iteraciones
(ver convención AGENTS.md).

## 6. Almacén vectorial (Qdrant) — pendiente

- `QdrantConfig` define conexión.
- `QdrantRecord` define el modelo de resultado.
- **`QdrantRepository` (clase) aún no existe** — solo `QdrantRecord` está
  declarado. Marcado como **Pendiente** en `05_Tasks_Inventario.md`.
- Uso previsto: búsqueda semántica sobre catálogo y/o feed (puntuación por
  relevancia). La integración concreta se documentará cuando se implemente.

## 7. Estado de sesión (no es BD)

`sessionProvider` (`lib\core\providers\app_providers.dart`) es estado en
memoria Riverpod (`Map<String, String?>`), **no se persiste en CouchDB**.
Su rol es retener token JWT / userID durante la sesión activa; la
persistencia de credenciales seguras se gestiona en el módulo Security
(`flutter_secure_storage` / `shared_preferences` — ver módulo D3).
