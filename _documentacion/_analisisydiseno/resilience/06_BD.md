# Documentación de Bases de Datos — Módulo Resilience

**Ruta código:** `lib\resilience\`
**Fecha:** 2026-08-13

## 1. Separación de Estructuras

### Estructuras internas (NO van a CouchDB)
- `ConnectionStatus` (`data_models\connection_status.dart`): estado de conectividad; efímero, del sensor.
- `PlatformInfo` (`data_models\connection_status.dart`): info de plataforma; efímero.
- `SyncState` (`data_models\connection_status.dart`): estado de sincronización; observable in-memory.
- `ResilienceEngine`, `ConnectionNotifier`, `PlatformNotifier`, `SyncNotifier`: lógica/estado Riverpod.
- Los répos abstractos y stubs (`StubConnectivityRepository`, `StubPlatformRepository`, `InMemorySyncRepository`).

### Estruturas que van a Base de Datos (potencial)
**Ninguna propia como entidad de dominio.** Sin embargo, la **cola de sincronización** (`InMemorySyncRepository._queue`) contiene `Map<String, dynamic>` payloads que representan operaciones pendientes a reintentar. Si se desea persistir la cola entre sesiones (para no perder operaciones offline al cerrar la app), esta cola **debería** persistirse — localmente (SQLite/Isar/SharedPreferences) o en CouchDB.

> **Importante:** Flutter **nunca posee credenciales CouchDB**; persiste vía backend Express. La cola de sync es típicamente local (offline-first), no en CouchDB. Lo siguiente describe opciones.

## 2. Cola de Sincronización (`SyncRepository`)

### Estructura: payload encolado (operación pendiente)

| Campo | Tipo Dart | Tipo JSON | Req | Descripción |
|---|---|---|---|---|
| `payload` | `Map<String, dynamic>` | `object` | ✓ | Datos de la operación a reintentar (tipo, endpoint, body, idempotencyKey, …) |

- **`SyncState`** (`isSyncing`, `lastSyncedAt`, `error`) describe el estado del proceso, no la cola.

### Opciones de persistencia

#### Opción A: Almacenamiento local (recomendado)
La cola de operaciones offline-first se persiste localmente (no en CouchDB) para sobrevivir entre sesiones:
- **SharedPreferences** (cola pequeña, serializada a JSON).
- **SQLite/Isar/Hive** (cola estructurada, consultable).

#### Opción B: CouchDB `motorsocial_sync_queue` (si se quiere sincronizar entre dispositivos)

```json
{
  "_id": "sync:uuid",
  "type_doc": "SyncOperation",
  "ownerId": "user:9999",
  "payload": { "operation": "create_activity", "body": { "..." } },
  "status": "pending",
  "createdAt": "2026-08-13T15:00:00.000Z",
  "retryCount": 0,
  "lastError": null
}
```

#### Consultas (Mango)
**1. Operaciones pendientes por usuario**
```json
{
  "selector": {
    "type_doc": "SyncOperation",
    "ownerId": "user:9999",
    "status": "pending"
  },
  "sort": [{ "createdAt": "asc" }],
  "limit": 100
}
```

#### Índices
```json
{ "index": { "fields": ["ownerId", "status", "createdAt"] }, "name": "idx_owner_status_created_at", "type": "json" }
```

> **Recomendación:** usar almacenamiento local (Opción A); la BD CouchDB dedicada (Opción B) es compleja y plantea el problema del "whose-device" del offline-first. Documentar la decisión al cablear.
