# Documentación de Bases de Datos - Módulo Identity

> Convenciones MotorSocial (ver `AGENTS.md`): DBs `motorsocial_*`; doc IDs con prefijo semántico (`user:uuid`, `perfil:uuid`); preferir Mango queries sobre MapReduce. Flutter nunca tiene credenciales CouchDB; los repositorios de este módulo son la abstracción, y el backend (repositorio separado, Node.js + `nano`) es quien opera la BD. Hoy los repositorios en `lib/identity/` son **stubs** (`Stub*`, `InMemory*`), por lo que el contenido de este documento es **objetivo** (basado en los contratos del módulo) salvo donde se indique "actualmente no implementado".

## 1. Clasificación de estructuras Dart

### 1.1 Estructuras que van a CouchDB (dominio persistente)

| Estructura Dart | Archivo | DB CouchDB destino | Prefijo Doc ID | Estado actual |
| :--- | :--- | :--- | :--- | :--- |
| `SocialUser` (identidad social) | `data_models/social_user.dart` | `motorsocial_usuarios` | `user:uuid` | Cascarón — sólo 3 campos (`id`, `displayName`, `photoUrl`). `UsersRepository` actual (`InMemoryUsersRepository`) es no-op. *(Pendiente ampliar y conectar al backend.)* |
| *(Implicita)* Perfil/credencial del usuario | (deducido del `AuthState.userId`/`accessToken` y de la convención `motorsocial_perfil_nutricional`) | `motorsocial_usuarios` (cuenta/credenciales), `motorsocial_perfil_nutricional` (perfil extendido) | `user:uuid` / `perfil:uuid` | No existe clase Dart que corresponda en este módulo; el backend gestiona credenciales. Flutter nunca posee creds CouchDB. |
| `RoleProfile` (perfil de rol y permisos) | `data_models/role_profile.dart` | (a) dentro del doc de usuario `motorsocial_usuarios` como sub-doc, o (b) colección `motorsocial_roles` por convención | `role:uuid` si se modela aparte | `RoleProfile` ya es serializable (`fromJson`/`toJson`); no hay repositorio que lo persista en este módulo. |

### 1.2 Estructuras internas (NO van a CouchDB)

| Estructura Dart | Archivo | Motivo de exclusión |
| :--- | :--- | :--- |
| `AuthState` | `data_models/auth_state.dart` | Estado de UI / sesión en memoria. Agrega `errorCode`/`errorMessage` que son de presentación, no de dominio persistente. |
| `SessionData` (`token`, `expiresAt`, `payload`) | `data_models/session_data.dart` | Es caché local de sesión/JWT. El `token` se guarda en `flutter_secure_storage`/`shared_preferences`, no en CouchDB. |
| `SocialIdentityContract` | `data_models/social_identity_contract.dart` | Envoltura derivada de `AuthState`. No es persistente. |
| `StubAuthRepository`, `StubSessionRepository`, `InMemoryUsersRepository`, `LocalSessionRepository` | `repositories/*` | Implementaciones internas (stubs); abstracción frente a la BD, no contenido. |

## 2. Estructuras a BD (detallado)

### 2.1 `SocialUser` — documento de usuario en `motorsocial_usuarios`

**Estructura Dart:**
```dart
class SocialUser {
  final String id;
  final String displayName;
  final String photoUrl;
  const SocialUser({required this.id, required this.displayName, required this.photoUrl});
}
```
*Nota: hoy no tiene `fromJson`/`toJson`. La siguiente especificación JSON marca el formato objetivo cuando se implemente `UsersRepository` real sobre el backend.*

**Diccionario de datos:**

| Campo | Tipo | Descripción |
| :--- | :--- | :--- |
| `_id` | String | Identificador CouchDB con prefijo semántico: `user:<uuid>`. |
| `_rev` | String | Revisión CouchDB (gestionada por la BD). |
| `type` | String | Discriminador de doc: `"SocialUser"`. |
| `id` | String | ID interno del usuario (igual al UUID sin prefijo, para joins). |
| `email` | String | (objetivo) Email de acceso. Ausente en la clase Dart actual. |
| `displayName` | String | Nombre visible en la red social. |
| `photoUrl` | String | URL del avatar/foto de perfil. |
| `passwordHash` | String | (objetivo) Hash bcrypt/argon2 gestionado por el backend — **nunca** en Flutter. |
| `roleKey` | String | (objetivo) Clave del `RoleProfile` asociado. |
| `createdAt` | int | Timestamp ms Epoch de creación. |
| `updatedAt` | int | Timestamp ms Epoch de última actualización. |

**JSON esperado (formato objetivo):**
```json
{
  "_id": "user:a1b2c3d4-5678-90ef-1234-567890abcdef",
  "type": "SocialUser",
  "id": "a1b2c3d4-5678-90ef-1234-567890abcdef",
  "email": "taller@ejemplo.com",
  "displayName": "Taller Hermanos",
  "photoUrl": "https://cdn.motorsocial.app/u/a1b2/av.png",
  "roleKey": "negocio",
  "passwordHash": "$argon2id$v=19$m=...$...",
  "createdAt": 1723526400000,
  "updatedAt": 1723526400000
}
```

**Acceso desde Flutter:** vía `UsersRepository.findByEmail(email)` y `UsersRepository.save(user)` (contrato en `repositories/users_repository.dart`). Implementación actual `InMemoryUsersRepository` es no-op.

### 2.2 `RoleProfile` — perfil de rol / permisos

**Estructura Dart:**
```dart
class RoleProfile {
  final String key;
  final String name;
  final List<String> permissions;
  // fromJson, toJson, hasPermission(permission)
}
```

**Diccionario de datos:**

| Campo | Tipo | Descripción |
| :--- | :--- | :--- |
| `_id` | String | Prefijo semántico `role:<uuid>` (si se modela como colección propia) o sin `_id` si va embebido en el doc de usuario. |
| `type` | String | `"RoleProfile"`. |
| `key` | String | Clave corta del rol (ej. `negocio`, `cliente`, `admin`). |
| `name` | String | Nombre legible (`"Negocio"`, `"Cliente"`). |
| `permissions` | Array\<String\ | Lista de permisos (ej. `["catalog:read", "post:write"]`). |

**JSON esperado (colección propia `motorsocial_roles` — sugerida):**
```json
{
  "_id": "role:negocio-001",
  "type": "RoleProfile",
  "key": "negocio",
  "name": "Negocio",
  "permissions": ["catalog:read", "catalog:write", "post:write", "review:write"]
}
```

**JSON esperado (variante embebida en `motorsocial_usuarios`):**
```json
{
  "_id": "user:a1b2c3d4-...",
  "type": "SocialUser",
  "role": {
    "key": "negocio",
    "name": "Negocio",
    "permissions": ["catalog:read", "catalog:write", "post:write"]
  }
}
```

*No hay repositorio de roles en este módulo; `RoleProfile` se provee como modelo de datos unterstützt, sin persistencia declarada.*

## 4. Consultas (Mango Queries)

### 4.1 Buscar usuario por email (objetivo, para `UsersRepository.findByEmail`)

```json
{
  "selector": {
    "type": "SocialUser",
    "email": "taller@ejemplo.com"
  },
  "limit": 1
}
```

### 4.2 Buscar usuario por `id` (prefijo `user:`)

```json
{
  "selector": {
    "_id": { "$eq": "user:a1b2c3d4-5678-90ef-1234-567890abcdef" }
  },
  "limit": 1
}
```

### 4.3 Listar usuarios por rol (objetivo)

```json
{
  "selector": {
    "type": "SocialUser",
    "roleKey": "negocio"
  },
  "sort": [{ "displayName": "asc" }],
  "limit": 50
}
```

### 4.4 Obtener un `RoleProfile` por `key` (si se modela como colección)

```json
{
  "selector": {
    "type": "RoleProfile",
    "key": "negocio"
  },
  "limit": 1
}
```

### 4.5 Indexar por `displayName` (paginación listado)

```json
{
  "selector": { "type": "SocialUser" },
  "sort": [{ "displayName": "asc" }],
  "limit": 20,
  "skip": 0
}
```

## 6. Vistas / queries adicionales

> MotorSocial **prefiere Mango queries** (sección 4) sobre MapReduce. No se definen vistas `_design/...` para el módulo Identity. Si se requiriese agregación (ej. `count` de usuarios por rol), preferir `_find` con índices (5.2) o un endpoint agregado en el backend Node.js, no una vista MapReduce.

### 6.1 Validación de existencia de email (objetivo, peek durante registro)

```json
{
  "selector": { "type": "SocialUser", "email": "taller@ejemplo.com" },
  "fields": ["_id"],
  "limit": 1
}
```
Retorna doc vacío si el email no existe → OK para crear cuenta; si existe → el backend rechaza alta duplicada.

## 7. Notas de seguridad (recordatorio de la arquitectura)

- Flutter **nunca** contiene credenciales CouchDB (ver `AGENTS.md`). Los repositorios de `lib/identity/` son el **contrato**; su implementación real llamará a la API Express (repositorio backend, `nano`) que sí opera CouchDB con el usuario `admin` (secreto en `defines.json`/`COUCHDB_PASSWORD`).
- El `passwordHash` y cualquier secreto permanecen fuera del cliente Flutter. El `SessionData.token` (JWT) se persiste localmente en `flutter_secure_storage` (iOS/Android) o `shared_preferences` (Web/Windows), **no** en CouchDB.
- Las implementaciones activas actuales (`StubAuthRepository`, `StubSessionRepository`, `InMemoryUsersRepository`, `LocalSessionRepository` no-op) deben sustituirse por las implementaciones reales que llamen al backend; el módulo Identity no debe implementar acceso directo a CouchDB desde el cliente.
