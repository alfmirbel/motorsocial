## 1. Separación de Estructuras

### Estructuras internas (NO van a CouchDB)
- `ActivityQuery` (`data_models\activity_contract.dart`): parámetros de consulta (`actorId`, `limit`), efímero.
- `FeedState`, `ConversationState`, `ReactionState` (`providers\*`): estado observable Riverpod in-memory.
- `ActivityContract` (`data_models\activity_contract.dart`): marker vacío (sin `const` en el árbol plano), reservado para futuras definiciones compartidas.

### Estructuras que van a Base de Datos
La única estructura serializable con semántica de dominio es **`SocialActivity`** (representa un evento social del feed). Representa una actividad o evento social en la plataforma (ej. alguien dio "Me gusta", un negocio publicó algo).

> **Importante:** en la arquitectura MotorSocial, Flutter **nunca posee credenciales CouchDB** y no escribe directamente en CouchDB; toda persistencia se realiza a través del backend Express (Node.js + `nano`). El `ActivityRepository` en Flutter es la abstracción que delega al backend. La definición de BD de aquí describe cómo **debería** almacenarse la actividad en CouchDB cuando se cablee el backend.

## 2. Estructura: `SocialActivity`

**Descripción:** Evento social del feed (like, comment, post, review, etc.) producido por un actor sobre un objeto de la plataforma.

### Diccionario de Datos

| Campo | Tipo Dart | Tipo JSON | Req | Descripción |
|---|---|---|---|---|
| `id` | `String` | `string` (`_id`) | ✓ | Identificador único de la actividad (prefijo `activity:`) |
| `actorId` | `String` | `string` | ✓ | ID del usuario o negocio que realizó la acción (p. ej. `user:uuid`) |
| `actorName` | `String` | `string` | ✓ | Nombre descriptivo del actor (desnormalizado para rendimiento) |
| `verb` | `String` | `string` | ✓ | Verbo de la acción (`like`, `comment`, `post`, `review`, …) |
| `objectType` | `String` | `string` | ✓ | Tipo de objeto sobre el que recae la acción (`producto`, `perfil`, `post`, `publicacion`, …) |
| `objectId` | `String` | `string` | ✓ | ID del objeto (p. ej. `post:1111`, `producto:2222`) |
| `payload` | `Map<String, dynamic>` | `object` | ✗ | Datos adicionales variables (texto del comentario, URL de imagen, etc.). Por defecto `{}` |
| `createdAt` | `int` | `number` (ms Epoch) | ✓ | Timestamp de creación en milisegundos desde Epoch |

> **Nota:** la clase `SocialActivity` actual **no** implementa `fromJson`/`toJson`; deberá añadirse al cablear el backend.

### Formato JSON Esperado

```json
{
  "_id": "activity:1234-uuid-5678",
  "type": "SocialActivity",
  "actorId": "user:9999",
  "actorName": "Taller Mecánico Hermanos",
  "verb": "post",
  "objectType": "publicacion",
  "objectId": "post:1111",
  "payload": {
    "text": "Nuevo servicio de escáner automotriz",
    "image_url": "https://..."
  },
  "createdAt": 1691234567890
}
```

## 3. CouchDB

### Nombre de la base de datos
- **`motorsocial_activity_feed`** (sugerida; el sharding depende del volumen por usuario).

> Alternativa: si los mensajes de conversación también se persisten como `SocialActivity` con `objectType: "mensaje"`, pueden vivir en la misma BD; si el volumen de mensajería es alto, separar a `motorsocial_mensajes` (Doc ID `mensaje:uuid`).

### Consultas (Mango Queries)

**1. Feed global (paginado, más recientes primero)**
```json
{
  "selector": {
    "type": "SocialActivity",
    "createdAt": { "$gt": 0 }
  },
  "sort": [
    { "createdAt": "desc" }
  ],
  "limit": 20
}
```

**2. Feed por actor (filtrado, paginado)**
```json
{
  "selector": {
    "type": "SocialActivity",
    "actorId": "user:9999"
  },
  "sort": [
    { "createdAt": "desc" }
  ],
  "limit": 20
}
```

**3. Actividades sobre un objeto concreto**
```json
{
  "selector": {
    "type": "SocialActivity",
    "objectType": "publicacion",
    "objectId": "post:1111"
  },
  "sort": [
    { "createdAt": "desc" }
  ],
  "limit": 50
}
```

### Índices Requeridos

**Índice por `createdAt`** (soporta ordenamiento cronológico inverso del feed)
```json
{
  "index": {
    "fields": ["createdAt"]
  },
  "name": "idx_created_at",
  "type": "json"
}
```

**Índice por `actorId` + `createdAt`** (soporta feed filtrado por actor)
```json
{
  "index": {
    "fields": ["actorId", "createdAt"]
  },
  "name": "idx_actor_created_at",
  "type": "json"
}
```

**Índice por `objectType` + `objectId` + `createdAt`** (soporta actividades de un objeto)
```json
{
  "index": {
    "fields": ["objectType", "objectId", "createdAt"]
  },
  "name": "idx_object_created_at",
  "type": "json"
}
```

### Vistas / Queries (MapReduce — alternativas)
> Por convención MotorSocial se prefiere Mango; estas vistas se documentan como referencia.
- **Vista `by_actor`** (`map`): `emit(doc.actorId, doc.createdAt)` para listar actividades por actor.
- **Vista `by_object`** (`map`): `emit([doc.objectType, doc.objectId], doc.createdAt)` para listar por objeto.
