# Documentación de Bases de Datos — Módulo Features

**Ruta código:** `lib\features\`
**Fecha:** 2026-08-13

## 1. Separación de Estructuras

### Estructuras internas (NO van a CouchDB)
- Todas las páginas (`LoginPage`, `FeedPage`, `CatalogPage`, `ChatPage`, `ProfilePage`, `HomePage`, `AccountPage`): UI/estado efímero.
- `AccountRepository` (abstract): contrato; su implementación concreta (cuando exista) delegará al backend.

### Estructuras que van a Base de Datos
**Ninguna propia.** Features es la **capa de integración/agregación** que consume BD de otros módulos:
- `FeedPage` lee `motorsocial_activity_feed` (Activity) vía `activityRepositoryProvider`.
- `CatalogPage` lee `motorsocial_catalog` (Catalog) vía `catalogRepositoryProvider`.
- `ChatPage` lee `motorsocial_grupos` (Social Graph) vía `groupProvider`.
- `ProfilePage`/`LoginPage` leen sesión de `motorsocial_usuarios` (Identity) vía `sessionProvider`/`AccountRepository`.

> Flutter nunca posee credenciales CouchDB; todas las lecturas se hacen a través de los providers/repositorios de cada módulo de dominio, que delegan al backend Express.

## 2. `AccountRepository` (cuando se cablee)

Cuando se implemente, `AccountRepository` operaciones CRUD sobre `SocialUser` (`motorsocial_usuarios`):

| Operación | Mapeo backend |
|---|---|
| `createAccount(user, secret)` | POST `/users` (crear `user:uuid` + hash de `secret`) |
| `getAccount(userId)` | GET `/users/<userId>` |
| `updateAccount(user)` | PUT `/users/<userId>` |
| `deleteAccount(userId)` | DELETE `/users/<userId>` |

El `AccountRepository` concreto (a crear) usará Dio con JWT interceptor (Security) y llamará al backend Express/nano, que persiste en `motorsocial_usuarios`. Documentado en `identity\06_BD.md`.

## 3. Estado Actual del Módulo

- `AccountRepository` es abstract sin implementación; no accede a CouchDB.
- Las páginas de lectura (Feed/Catalog/Chat/Profile) sí consumen providers reales, pero esos providers resuelven a stubs in-memory (ver BD de cada módulo de dominio).
- No se requiere crear BDs `motorsocial_*` para Features; toda persistencia se documenta en el módulo de dominio correspondiente.
